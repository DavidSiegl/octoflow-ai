## `prune` removes the leftover worktree of a finished run, so its branch can go too

- **A `--worktree` run's worktree no longer outlives its merged pull request.** A run removes its worktree once the pull
  request is open, but git refuses when something in it changed meanwhile, and the run only logs that. The worktree then
  stayed for good, and kept its branch checked out, so `prune` kept the branch as well. `prune` now removes such a
  worktree, under `.orchestrator/worktrees/`, once its pull request is merged or closed for 14 days, and then deletes the
  branch.
- **A worktree with unfinished work stays.** The worktree must have no uncommitted changes, have the run's own branch
  checked out (or a detached HEAD), and sit at the pull request's head commit or behind it. Otherwise it stays with
  its branch, and `prune` prints why, such as `worktree … has uncommitted changes`, `… now holds branch …` or
  `… has commits PR #7's head lacks`; so does one git refuses to remove, a locked one for example. `--dry-run` says
  what would be removed and changes nothing.
- **Ignored files go with the worktree.** Files git ignores, such as a hand-made `.env`, are not counted as changes
  and are deleted with it, as `close` does for a failed run's worktree. Copy out what you want to keep before
  `prune` runs, or before your next run opens its pull request, which prunes too.
- **A worktree directory you deleted by hand no longer keeps its branch.** `prune` first runs `git worktree prune`, so
  git stops counting the branch as checked out. This forgets every worktree of the repository whose directory is gone,
  not only the runs'.
- **Your own worktrees are never touched.** Only a worktree a run's state names, directly under
  `.orchestrator/worktrees/`, is considered. A finished `--no-pr` run's worktree, which holds the change, and a failed
  run's, which `close` handles, stay as they were.
