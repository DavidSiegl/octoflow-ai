## A run record says how each step is labelled, where it loops, and whether the run opens a pull request

- **`list --json` and serve's `/runs` and `record` events** give each of a run's `steps` three more keys:
  `role_label`, the workflow's label for the step's role (`Builder`, or what a workflow file's `[roles]` says);
  `loop_to`, the step a `CHANGES_REQUESTED` from this step sends the run back to, null for a step that gives no
  verdict; and `quality_gated`, true when the quality loop follows, or followed, the step's turns in this run, so
  only in a run started with `--quality-gate`. The record gains `pull_request`, false for a `--no-pr` run. The
  existing keys keep their meaning and the document's `version` stays 1.
- These are what the desktop app's run map will draw the run's stages and loops from; the app does not show them
  yet.
