## More than one verdict step in a workflow

A workflow file may now give `loop_to` to more than one step, such as a Tech Lead's review that goes back to the
Builder followed by a Product Manager's acceptance that goes back to the Builder too.

- **A round runs the verdict steps in order** and ends at the first that requests changes: the run goes back to that
  step's `loop_to` in the next round, so a later verdict step never judges a change an earlier one rejected.
- **Every verdict step judges the change the round ends with.** A workflow is refused if a verdict step loops back
  past the first verdict step, or if a step between the first verdict step and the last edits the code.
- **`--max-rounds` bounds all of them together**: there is one round counter. In the last round, a verdict step that
  requests changes ends the round, and the run goes on past the last verdict step.
- **The run approves only if every verdict step approved the last round.** A run stopped between two verdict steps
  is not shown as approved. The pull request names each verdict of the last round and shows each verdict file;
  `summary.md` lists each step's verdict per round; `list` says which step sent a run back, as in
  `CHANGES_REQUESTED by accept`; `list --json` and serve's `/runs` carry a new `verdicts` key; and `show` prints a
  `verdicts` section and the last verdict file written.
- **A new placeholder, `{findings}`**, names the verdict file whose request for changes started the round. The
  built-in Builder prompt for a later round, `FIX_PROMPT`, now names it in place of `{prev_review_path}`, so the
  Builder reads the findings of whichever verdict step sent the round back, and it opens "Changes were requested"
  rather than "The Reviewer requested changes".
- A verdict step that earlier ones kept from judging gets its first prompt on its first turn, even in a later round.
- **`proof_command`** runs the proofs of the first verdict step only.
- `state.json` records each verdict step's verdict per round in a new `verdicts` field. A run saved by an earlier
  release, without it, still resumes, lists and shows.
- **The `product-team` example workflow has the Product Manager accept the change** once the Tech Lead approves it.
  The Product Manager's own agent, the one that ran the interview, judges the change against the requirements'
  acceptance criteria and success measures alone, in business terms, and writes `acceptance-{n}.md`. A request for
  changes from either goes back to the Engineer, whose prompt for the next round names the file that sent it back.
  The Tech Lead's review no longer opens with a summary for the Product Manager.

### Breaking: a `FIX_PROMPT.md` prompt file must use `{findings}` for a new run

A prompt file must use exactly the placeholders of the text it replaces, so a `FIX_PROMPT.md` written for an earlier
release, which names `{prev_review_path}`, is now refused, and `run` and `drain` stop before any agent starts. The
error names the placeholder: "placeholder {prev_review_path} … is not one this template takes; FIX_PROMPT takes
{build_path}, {findings}". Replace `{prev_review_path}` with `{findings}` in the file.

This covers only prompt files read for a new run. A run that an earlier release started with such a file saved its
text, and it still resumes, lists and shows: in such a run `{prev_review_path}` names the same file `{findings}`
would.
