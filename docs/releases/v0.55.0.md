## serve starts runs

`orchestrator serve` was read-only for runs; it now starts them too, for the desktop app's coming run form.

**`POST /run`** (token and origin checked as for every request; the project by `?cwd=` and `?machine=`) takes a JSON
body of task, workflow, agent, model, role_agents, role_models, no_pr and worktree, opens a new workspace in this
machine's herdr server, labelled as a run labels its own, and runs serve's own `orchestrator run` in it, so the run
can be watched and interrupted there and outlives serve. A project on a machine is started from here as
`run --machine M --cwd DIR`, as from the CLI. It answers 201 `{"run": ID}` once the run has saved its state, 422 with
the pane's last lines when the command ended without one, and 202 `{"run": ID, "listed": false}` when neither
happened within 30 seconds. Without a herdr server here it answers 502 `no herdr server here; start herdr`. A bad body
is refused with 400 before the project is reached.

**`GET /workflows`** lists the workflows `run --workflow` offers, each with its description and its roles' labels,
harnesses and models, and the harnesses there are.

**`run --run-id ID`**, hidden from help, gives the run that id instead of a new one; serve uses it to wait for exactly
the run it started.
